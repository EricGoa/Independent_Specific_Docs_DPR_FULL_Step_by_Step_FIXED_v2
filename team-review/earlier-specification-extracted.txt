INTRODUCTION
This document specifies the Official Document and Registry of Notification Section's (ODRNS) application of the Common Specification for Information Packages (E-ARK CSIP) and the Specification for Submission Information Packages (E-ARK SIP). The specification SHALL be used for the creation of a SIP (Submission Information Package) when submitting WTO official documents to the long-term digital preservation repository.
This document will be continuously maintained, updated, and version-managed.

Information packaging specifications: E-ARK
This specification builds on the following E-ARK information packaging specifications, which define the baseline structural and metadata requirements for all information packages:

E-ARK Common Specification for Information Packages (CSIP), version 2.2.0, 17 May 2024 [EARK_CSIP]
E-ARK Submission Information Package (SIP), version 2.2.0, 17 May 2024 [EARK_SIP]
E-ARK Archival Information Package (AIP), version 2.2.0, 17 May 2024 [EARK_AIP]
Common Specification for Preservation metadata, version 1.0.1, 17 May 2024 [CS_PREMIS]
The application defines WTO ODRNS-specific requirements on top of this baseline. Where this specification is silent, the E-ARK base specifications apply.
This document currently specifies the ODRNS application for SIP creation.

ODRNS E-ARK application profile

Introduction
This section documents how E-ARK CSIP version 2.2.0 and E-ARK SIP version 2.2.0 SHALL be applied for packaging information in a Submission Information Package (SIP) when transferring official documents and their metadata to the Official Document Digital Preservation Repository (ODDPR).
No modifications have been made to the METS schema or the E-ARK extension schemas (DILCISExtensionMETS and DILCISExtensionSIPMETS); all are applied in their original versions. The METS profile follows that defined in E-ARK CSIP and E-ARK SIP. The E-ARK controlled vocabularies are used as specified and supplemented, where necessary, by WTO-specific vocabularies applied in OTHERTYPE elements. These supplementary vocabularies are not subject to schema validation.

The application profile also provides for each SIP to include an XML document containing additional information about the package and its contents, beyond what is captured in the METS document. This document is optional but may be used, for example, when describing packages and files where the packaged content is not structured in accordance with a content-type-specific specification. Where used, the document SHALL be named additionalPackageInfo.xml and placed in the documentation folder. It is validated against the SNAadditionalPackageInfo.xsd schema.
[Note: Develop ODRNS specific version of SNAadditionalPackageInfo.xsd]

SIP Folder Structure and Metadata
This section sets out the required structure and contents of an ODRNS submission information package (SIP). Every SIP submitted under this application profile SHALL include a METS document (METS.xml) that describes the package and its contents. A SIP MAY additionally include an additionalPackageInfo.xml document providing supplementary package-level information beyond what is captured in the METS document.
The content of a submission information package (SIP) SHALL always be arranged according to the following defined folder structure with prescribed folder names, as set out below:

All folders SHALL be present in every package, including those that contain no content.

Information Package Root Folder
All content in the submission information package MUST be included in a single root folder (item 1 in the diagram; see also CSIPSTR1). The folder name SHALL follow this naming convention:
[SIP]_[YearOfSubmission]_[6-digit_sequential_number]_[dol]_[JOB_ID]

A complete folder name would read: SIP_2026_000001_dol_2025_3033

Packages archived in an archive file format such as ZIP or TAR MUST be unpacked to a single root folder. 

The root folder SHOULD be named with the same ID or name of the Submission Information Package, that is the value of the package METS.xml root <mets> element @OBJID attribute (see CSIPSTR2).

The JOB_ID is also used as a common identifier across all file names, facilitating comprehension and enabling the attribution of any orphan files to their intellectual entity should they become separated from the package.

NOTE: In the ODRNS application, a separate SIP is created for each intellectual entity — understood in the PREMIS sense [CS_PREMIS] as a set of content treated as a single unit for management and description. In the Documents Online context, this corresponds to a single official document as identified by its document symbol (e.g. G/SPS/N/CAN/1591).


METS document 
The METS document (item 2) MUST be placed directly in the root folder (see also CSIPSTR4). Only one METS document SHOULD exist per SIP. 

The file SHOULD be named according to the following convention:
[METS]_[JOB_ID].xml  

The file name would read: METS_2025_3033.xml
If additionalPackageInfo.xml is used for additional description of the package, a reference to it SHOULD be made from the METS document.

Metadata folder
A folder named metadata MUST exist under the SIP root folder (item 3). 

Note: All metadata for both the package and the representations (METS, DOME, DC and PREMIS metadata) are located in the Information Package folder rather than in the representation folders.
This is a simplified implementation permitted by [EARK_CSIP] and is reasonable in scenarios where the amount of data and metadata is limited.

Descriptive folder
A folder named descriptive MUST exist under the metadata folder (item 4).


Preservation folder
A folder named preservation MUST exist under the metadata folder (item 5).

Other
A folder named other MUST exist in the metadata folder (item 6). Any other metadata, such as rights metadata, SHALL be placed here (if available).

Representations
The Information Package root folder MUST include a folder named representations (item 7). 

The representations folder MUST include the sub-folders for each individual representation and SHOULD be named rep_1 and rep_2 (item 8 and item 13).

The source files of official documents (e.g. DOC, DOCX, XLS, XLSX, MDB, WPF) MUST be placed in the sub-folder named rep_1.

The derivative/outcome files of official documents (i.e. PDF or PDF/A) MUST be placed in the sub-folder named rep_2. If notification attachments exist, these MUST also be placed in the sub-folder named rep_2.

Note: According to PREMIS Version 3.0 "[a] representation is a set of files, including structural metadata, needed for a complete and reasonable rendition of an Intellectual Entity. For example, a journal article may be complete in one PDF file. This single file constitutes the representation. Another journal article may consist of one SGML file and two image files. These three files constitute the representation. A third article may be represented by one TIFF image for each of 12 pages plus an XML file of structural metadata showing the order of the pages. These 13 files constitute the representation." [PREMIS]

Schemas folder
A folder named schemas  (item 19) MUST exist in the Information Package root folder. This folder is designated for holding the XML schema documents for all structured data and metadata files in the package. All XML schemas used in the package SHALL be placed here. The schema version included SHALL correspond to the version used in the package, not necessarily the latest available.


Documentation folder
A folder named documentation (item 20) MUST exist in the Information Package root folder.

This folder is a valuable resource for understanding the structure, meaning, and organization of the data, making it an essential component of the package for both current users and future stakeholders [EARK_SIP]. The folder MUST include at minimum one of the documents listed below to ensure the package contains supporting materials. Documentation that SHOULD be included is:

Submission process documentation
Current version of DOL Cataloguing Manual
Documents Online Metadata Elements (DOME) guide
Any script used to migrate, normalize or prepare the content of the information package (e.g. Aspose PDF/A creation script)
DOL value lists used in the descriptive metadata (e.g. Subject, Body, Organization, Articles, Products etc.)
CRN notification description procedures

If additionalPackageInfo.xml is used, it shall be placed in the documentation folder and referenced from the METS document.

Note: It is recommended to include the current versions of any value lists and guidance documents at the time of SIP preparation. This ensures that the package documents the values and definitions that were in use when it was created. Linking to externally maintained namespace documents, vocabulary lists, or similar resources is not advised — such links will always resolve to the latest version rather than preserving the version used at the time of packaging.

METS Structure and Element Reference
The following section describes how the METS.xml document SHALL be constructed. It follows the overall structure of the E-ARK CSIP and E-ARK SIP Specifications. 

The information is presented in tabular format. The columns are described below:

Column
Description
ID
The E-ARK CSIP or SIP requirement identifier, e.g. CSIP1 or SIP2
Description
The requirement name in bold, the element or attribute path in code font, and a description of its purpose and usage including any ODRNS-specific values or examples
Card & Level
The cardinality and requirement level as defined in the E-ARK CSIP and SIP specifications, e.g. 1..1 MUST or 0..1 MAY
ODRNS Appl.
The requirement level as applied in the ODRNS implementation. Where this differs from the E-ARK cardinality, the ODRNS requirement takes precedence.


Cardinality (card. column) specifies how many times an element may or must appear:

Value
Meaning
1..1
Exactly once — mandatory, exactly one occurrence
1..n
One or more - mandatory, may repeat
0..1
Zero or one — optional, at most one occurrence
0..n
Zero or more — optional, may repeat

Requirements that are not used in the ODRNS application are either marked as NOT USED in the ODRNS Appl. column or omitted from the tables entirely. The absence of a requirement from a table indicates that it is not used in the ODRNS application.

PREMIS Preservation Metadata
This section specifies how PREMIS 3.0 preservation metadata SHALL be created and structured within a WTO ODRNS Submission Information Package (SIP). It forms part of the ODRNS application profile and SHALL be read in conjunction with the E-ARK Common Specification for Preservation Metadata [CS_PREMIS], version 1.0.1, the PREMIS Data Dictionary for Preservation Metadata [PREMIS], version 3.0, on which it is based. Where this section is silent, [CS_PREMIS] applies.


Purpose
Preservation metadata is the information a repository uses to support the long-term preservation of digital objects — maintaining their viability, authenticity, integrity, and renderability over time. In the ODRNS application, preservation metadata serves two related purposes: it records the technical characteristics of the digital objects packaged in the SIP at the time of submission, and it establishes a provenance record of the actions taken on those objects before and during ingest. The standard used for preservation metadata in this application is Preservation Metadata: Implementation Strategies (PREMIS), maintained by the Library of Congress, and implemented in accordance with the E-ARK Common Specification for Preservation Metadata [CS_PREMIS]. Although this section specifies PREMIS usage in the context of SIP creation, the same specifications are intended to apply to preservation actions undertaken after ingest. Where preservation actions are carried out within the repository — such as format migration, fixity checking, or normalisation — these SHOULD also be recorded using PREMIS, and the specifications set out here are expected to extend accordingly to the Archival Information Package (AIP), the details of which will be addressed in a future AIP specification.

The PREMIS data model
PREMIS is organised around four entity types, each of which can be recorded in the PREMIS XML document:
Object — a discrete unit of information subject to preservation. In PREMIS 3.0, objects may be of entity type Intellectual Entity (a set of content treated as a single unit, such as a WTO official document), Representation (the set of files needed for a complete rendition of the intellectual entity), File (a named sequence of bytes known to an operating system), or Bitstream (data within a file with meaningful preservation properties). Bitstreams are not used in the ODRNS application.
Event — an action that involves or affects at least one object or agent known to the repository, such as format identification, checksum calculation, or ingest.
Agent — a person, organisation, or software system associated with events in the life of an object, or with rights attached to an object.
Rights — an assertion of one or more rights or permissions pertaining to an object or agent.
The entities are linked by identifiers: events reference the objects they affect and the agents that performed them; agents may be linked to rights statements; objects carry relationships to other objects and to the events that created or transformed them.

Placement in the SIP
Each SIP SHALL contain exactly one PREMIS XML document. It SHALL be placed in the metadata/preservation/ folder and named according to the convention {JOB_ID}_premis.xml (e.g. 2025_3033_premis.xml). The PREMIS document SHALL be referenced from the <amdSec> of the METS document via the <digiprovMD> element, as specified in section 5.7.1. The PREMIS XML schema (premis.xsd) SHALL be included in the schemas/ folder of the SIP.

Use of PREMIS
The tables in this section follow the structure of [CS_PREMIS] and use the same requirement IDs where applicable. Requirement IDs prefixed PM are drawn directly from [CS_PREMIS]; the Card & Level column reflects the cardinality and conformance level as defined in [CS_PREMIS], while the ODRNS Appl. column specifies how the requirement is applied in this profile, which may differ from [CS_PREMIS]. Requirement IDs prefixed ODPM are defined by the ODRNS application profile and have no counterpart in [CS_PREMIS]; the Card & Level column reflects the ODRNS application requirement for these entries. For the full normative context, readers should consult [CS_PREMIS] and the PREMIS Data Dictionary [PREMIS] alongside this section.

A warning was generated by the event, indicating that it needs to be evaluated. Also includes partial success, e.g. a Schematron validation message like “you should probably include this information if you can”. URI: http://id.loc.gov/vocabulary/preservation/eventOutcome/war

File Naming Conventions
This subsection consolidates all file and folder naming conventions used in the ODRNS application. These conventions ensure that files can be identified, attributed to their intellectual entity, and located within the SIP or AIP, even if separated from their original context. 

The JOB_ID — described in section 5.2.1 — is the common identifier used in most filenames within the SIP.

Package-level folders

Element
Naming convention
Example

AIP root folder

Content files (rep_1 and rep_2)
Main document files in rep_1 (source) and rep_2 (PDF/A derivatives) follow either of two patterns depending on whether the document is single-part or multi-part:
Element
Naming convention
Example
Main document file (single-part)

Main document file (multi-part)
{JOB_ID}_{PART_NUMBER}_{lang}.{ext}
2025_3033_01_en.docx
Trilingual file (single-part)
{JOB_ID}_mul.{ext}
2025_3033_mul.pdf
Trilingual file (multi-part)
{JOB_ID}_{PART_NUMBER}_mul.{ext}

Where:
JOB_ID — defined in §5.2.1.
PART_NUMBER — two-digit zero-padded sequential number identifying the part (01, …). Omitted for single-part documents.
lang — two-letter language code (see Language code mapping below).
