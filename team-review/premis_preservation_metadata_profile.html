PREMIS preservation metadata — profile

Package PREMIS file for DOL SIPs and AIP versions

Author

Torsten Fratzke

Classification: Internal · Status: v0.4 Draft, not issued · UUID: 77a9a258-b35b-4121-af6f-3e91ed7fc602 · Created: 2026-10-07 · Modified: 2026-10-13

Note

Work in progress. This profile is being developed alongside the first iteration of the pipeline (the proof of concept), as the packages it produces are reviewed against it step by step. Rules, examples and controlled values are adjusted as that review proceeds. Drafts are numbered v0.n; v1.0 will be the approved edition, issued when the pipeline goes live. Until then, any requirement may change.

1 Purpose and scope

This profile specifies how [PREMIS] preservation metadata is created and structured in the DOL digital preservation pipeline (described in [DPR-WORKFLOW]): in each SIP the pipeline builds, and in each AIP version it commits to the DPR/AIP repository. It governs every component of the pipeline that writes PREMIS. Beyond validity against the PREMIS 3.0 schema, it sets the constraints specific to this repository: the semantic units required, their controlled vocabularies and their permitted values.

Writing sides. The specifications distinguish two sides of the pipeline by function, not by implementation: the preparation side, steps 0–7 of the workflow, ending with the bagged SIP; and the ingest side, steps 8–9, from bag verification to the OCFL commit. Each side may be implemented by any number of scripts. The software named on an event as its executing program is the software that did the work: the script itself where it acts directly, or the tool it calls where that tool performs the act, as for conversion, validation and format identification (see the Event catalogue).

Three artefacts in the AIP describe it, each with a distinct job:

  • PREMIS (metadata/preservation/{JOB_ID}_premis.xml) — preservation description, chiefly provenance: what the package holds, how each held byte came to be, and who or what acted on it.
  • METS ({JOB_ID}_mets.xml) — structure: the file inventory of the package, the representation divisions, and the references to DOME and PREMIS.
  • The OCFL inventory (inventory.json) — versioning and storage fixity: which bytes make up each version, their SHA-512 digests, and the commit of each version (created, user, message).

Description of the document itself is the DOME record’s, at metadata/descriptive/{JOB_ID}_dome.xml, and is outside this profile.

PREMIS is the authoritative record of the lineage of the held content: how each held byte came to be. Tool reports and logs held in the package (validation, QA, format identification, conversion) are evidence linked from PREMIS events, not separate records of lineage. The commit of each version is recorded in the inventory; operations on the stored object after commit are recorded in the OCFL object’s logs/; facts that never became held lineage are recorded in the run report (see Provenance outside PREMIS).

Versions and editions. In this profile, version means an OCFL version: a state of the object’s stored content, created by any change — a language added, a re-issue, a descriptive metadata change, a correction (see Modification by version type). It is not an edition of the document. Each language version of a document arrives as it is published in DOL, and each arrival creates a new version; the languages held in each version are recorded on SIP creation (DPM111), and completeness is not awaited.

Out of scope. Not governed by this profile: the root METS, governed by [METS-PROFILE]; the content of the DOME record; representation-level PREMIS, which is not written, the root METS being compound ([METS-PROFILE], DME2); extraction of technical metadata (file properties such as page count, fonts or colour spaces). Outside release 1 of the pipeline, and so not specified here: PREMIS for legacy material, environments and obsolescence-driven migration, and events the repository performs on a held AIP, such as fixity audits (see Open items).

Amendment. This profile is amended as the pipeline, the repository or the preservation requirements change. Each amendment is issued as a new edition of this document, with its version and modified date updated. Requirement identifiers are allocate-once (see Specifications): an identifier, once cited, never comes to denote a different requirement. PREMIS files already committed to OCFL are not rewritten when the profile changes; later OCFL versions append to them under the edition then in force (DPM4).

4 Conventions

4.1 Requirement levels

The key words MUST, MUST NOT, SHOULD, SHOULD NOT and MAY in this profile are to be interpreted as described in BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all capitals. In lower case they carry their ordinary meaning and state no requirement.

Level Meaning in this profile
MUST Required. A PREMIS file, or a pipeline step, that does not meet the requirement does not conform to this profile.
MUST condition Required when the stated condition holds (e.g. MUST for masters, MUST where PRONOM gives one); not written when it does not.
SHOULD Recommended. A writer may depart from it in a particular case for a documented reason, having weighed the consequences; the reason is recorded in the run report.
MAY Optional. Writing it or not are both conformant.
NOT USED Not written. The pipeline MUST NOT write the unit, and its validation before commit (DPM10) rejects a file that contains one. A unit found in a PREMIS file already committed is disregarded by readers and does not make that file non-conformant. Semantic units of the PREMIS Data Dictionary not cited in the specifications are NOT USED.

In this edition of the profile every requirement is MUST, conditional MUST or NOT USED; SHOULD and MAY are defined for later amendments.

4.2 Notation

  • {JOB_ID} stands for the object’s JOB_ID (e.g. 2026_012017); premis.xml and METS.xml denote {JOB_ID}_premis.xml and {JOB_ID}_mets.xml by role.
  • Values in square brackets and capitals, such as [ENGINE-VERSION], are placeholders for values still to be confirmed (see Open items).
  • UUIDs, digests, sizes, times and agent names in examples are illustrative; a digest shortened with … is 128 characters in full.
  • Terms are defined in the Glossary.

5 Placement and file model

One package PREMIS file per SIP and per AIP version. Each SIP carries one PREMIS file, and each AIP version holds one, at the same path: metadata/preservation/{JOB_ID}_premis.xml, relative to the bag’s data/ directory in a SIP and to the OCFL version’s content/ directory in an AIP (e.g. metadata/preservation/2026_012017_premis.xml). The AIP version’s file is the SIP’s with the ingest side’s additions (DPM117).

File names. The PREMIS file and the root METS carry the object’s JOB_ID as a prefix: {JOB_ID}_premis.xml and {JOB_ID}_mets.xml, the latter at the root of content/. The prefix makes either file identifiable when copied out of its package. The DOME record is held at metadata/descriptive/{JOB_ID}_dome.xml.

Canonical names. Every held file has a canonical name, built from the JOB_ID and, for a file of one language version, its language code ({lang}, from vocODRNSLanguage). A file acquired from DOL is renamed to its canonical name (DPM105) and keeps its DOL name in originalName (DPM63); a file the pipeline produces is written under its canonical name. Nothing else from DOL, such as its drive, folder path or file name, enters the name. {ext} is the extension of the DOL file, in lower case.

The published PDF is not held and has no canonical name; it is described under its DOL name (DPM40).

Referenced from root METS. The root METS references this file once, with its SHA-512, in mets/amdSec/digiprovMD/mdRef, as [METS-PROFILE] sets out (DME57–DME71): @MDTYPE="PREMIS", @MDTYPEVERSION="3.0", @MIMETYPE="text/xml", @LOCTYPE="URL", @xlink:type="simple", @xlink:href="metadata/preservation/{JOB_ID}_premis.xml", the file’s size in @SIZE, @CHECKSUMTYPE="SHA-512", the file’s SHA-512 in @CHECKSUM, and @STATUS="CURRENT" on digiprovMD.

Versioned by OCFL, not by file name. Every OCFL version writes a new premis.xml at the same logical path, since every version appends at least its packaging and ingest events (DPM4). The prior bytes remain in the earlier version and are read from that version’s state. A version state holds exactly one PREMIS file, and its name is the same in every version: no file is ever named for a version (2026_012017_premis_v2.xml is forbidden). The version is carried by the OCFL version directory, the inventory, and the AIP creation event (DPM113).

Schema location. The root element declares the PREMIS 3 namespace and a package-local schema location:

<premis xmlns="http://www.loc.gov/premis/v3"
        xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
        xsi:schemaLocation="http://www.loc.gov/premis/v3 ../../schemas/premis.xsd"
        version="3.0">

Encoding. See DPM13.

Element order. The PREMIS 3.0 schema fixes the entity sequence: objects, then events, then agents, then rights. Within each, elements carried from the predecessor keep their place, and the elements a version adds follow them (DPM4), so that each version’s file begins with its predecessor’s elements, entity by entity. Within the elements one version adds: objects by intellectual entity, then representations, then files in logical-path order, a published PDF (which has no logical path, DPM40) immediately before the master derived from it; events in chronological order; agents in order of first reference. A relationship added to an existing object follows that object’s existing relationships (DPM4). The order carries no semantics; it exists so that two correct writers produce comparable files, and so that a version’s additions can be checked as an extension of its predecessor.

6 Provenance outside PREMIS

PREMIS records the lineage of the held content: the objects, relationships, events and agents defined in this profile’s tables, and nothing else (DPM6). Three other records carry what PREMIS does not: the OCFL inventory, the OCFL object’s logs/ directory, and the run report. Each is a record of a different kind, and none duplicates PREMIS.

6.1 Excluded facts

Failed attempts: failed validations, rejecting QA decisions, rejections, masters superseded before commit and their purge, failed bag verifications Resolved before the version is committed; not part of the held lineage Run report
Batch selection and metadata export Batch administration; only the selection basis and batch identifier matter to the object Run report; the basis and batch_id are carried on SIP creation (DPM111)

6.2 The OCFL inventory

Every OCFL object carries an inventory, inventory.json, at its root, with a digest sidecar (inventory.json.sha512); both are required by [OCFL] §3.6–3.7. OCFL recommends, and this repository keeps, a copy of the inventory as it stood at each version in that version’s directory, so the record of every version survives even if the root inventory is damaged. OCFL software writes the inventory at each commit; it is not a PREMIS document and is not written under this profile’s rules, save for the commit record the ingest side supplies (DPM14). It is, however, the authoritative record of four things PREMIS leaves to it: what each version contains, where its bytes are, the fixity of every file, and the commit of each version.

Inventory element Records What it answers
id The object’s identifier, urn:uuid:{object UUID} Which object this is; the same UUID as the PREMIS intellectual entity and the root METS @OBJID of the AIP (DPM23)
head The latest version, e.g. v3 Which version is current
digestAlgorithm sha512 How every digest in the inventory was computed
manifest Each distinct bitstream’s digest, with the content path where its bytes are stored Where a file’s bytes physically are. An unchanged file is stored once, in the version that first wrote it, and carried forward by reference
versions/vN/state Each logical path in version N, with the digest of its content Exactly which files make up version N, and their fixity. Comparing the states of two versions shows what a version added, replaced or removed
versions/vN/created The date and time version N was committed (RFC 3339) When the version entered the repository: the commit and accession of that version
versions/vN/user The name and e-mail address of the person who authorised the commit of version N Who is accountable for the version; the software that committed it is the executing program of the AIP creation event (DPM113)
versions/vN/message Free text recording why version N was created Why the version exists: its selection basis
inventory.json.sha512 The SHA-512 of the inventory itself Whether the inventory has been altered

The inventory copies differ in a defined way. The root inventory is identical to the copy in the latest version directory. Each earlier copy is the inventory as it stood when its version was committed, frozen with that version: it records the object’s versions up to its own, and its version blocks agree with the corresponding blocks of the root inventory ([OCFL] §3.7). For JOB_ID 2026_012017 at v3:

File head versions it contains manifest covers
v1/inventory.json v1 v1 bytes written in v1
v2/inventory.json v2 v1, v2 bytes written in v1 and v2
v3/inventory.json = root inventory.json v3 v1, v2, v3 bytes written in v1, v2 and v3

The root inventory therefore holds the object’s complete history: each version’s state lists every file in that version, not only its changes, and nothing is removed from the manifest when a file is superseded. If the root inventory is damaged, the latest version’s copy replaces it exactly; an earlier copy still gives a complete, digest-verified record of every version up to its own.

What follows for PREMIS:

  • Commit and accession. PREMIS does not record the commit of the version that contains it; the version block does (created, user, message).
  • Physical location. PREMIS carries no storage (DPM64): the manifest resolves every logical path to its bytes, in whichever version holds them.
  • Currency. Whether a file is the current one at a logical path is answered by the head state, not by PREMIS, which keeps describing superseded files (DPM4).
  • METS and PREMIS fixity. The digests of METS.xml and premis.xml are recorded only in the inventory, since neither can carry its own.
  • Fixity of held files. For every held file the inventory and PREMIS record the same SHA-512 (DPM12); the inventory is the one OCFL tools verify.

6.3 The OCFL logs/ directory

The OCFL object root may hold a logs/ directory for records of actions taken on the stored object ([OCFL] §3.8). It sits outside the versions: it is neither versioned nor covered by the inventory’s fixity, and may be added to without creating a version. It records operations after commit that change nothing in the object, beginning with the removal of the bag from staging; its format is to be decided (see Open items).

6.4 The UUID registry

The UUID registry is the repository’s complete list of every UUID ever given: to objects, representations, files (held files, published PDFs, reports, DOME records), events, agents, batches, SIPs and rights statements, including those of attempts that never reached an AIP. It answers whether a UUID has ever been used, and which JOB_ID it belongs to. It is a reservation list, not a provenance record: it never says what was done, only that a UUID exists.

At about 10,000 documents a year and some 60 UUIDs per new document, the UUID registry grows by several hundred thousand rows a year. That rules out a spreadsheet (row limit; unsafe concurrent writes) and leaves two forms: a CSV file, which needs nothing beyond the pipeline’s scripts, or a table in an SQL Server database, which enforces uniqueness and append-only access itself and stays fast at any size. The columns are the same in either form.

6.5 The run report

The run report is a retained per-batch record outside the AIP (location under DPR/ to decide; see Open items). It records what happened to items and attempts that never became held lineage, and the reason for any departure from a requirement at level SHOULD (see Conventions). It is not a provenance store for objects and never overrides PREMIS.

7 Specifications

The information is presented in tabular format. The columns are described below:

Column Description
ID The requirement identifier, DPMnn. Identifiers are allocate-once: they were numbered in document order when first drafted; a requirement added later takes the next free number and is placed where it belongs; a withdrawn requirement keeps its ID and is marked withdrawn.
PREMIS unit The number of the semantic unit in the PREMIS Data Dictionary, version 3.0 [PREMIS], that the requirement governs (e.g. 1.1 objectIdentifier, 1.5.4.2.1 formatRegistryName); for an element encoding, the unit it encodes (object/@xsi:type encodes 1.2 objectCategory). — where the requirement governs the file or the process rather than a semantic unit. Catalogue entries cite the parent unit they instantiate.
PREMIS obligation The obligation the PREMIS Data Dictionary 3.0 gives the cited unit: Mandatory, Optional, or Conditional where it sets a specific condition (e.g. at least one of several sub-units). For a sub-unit, the obligation applies when its container is present. It is the obligation of the unit, not of each occurrence: a second objectIdentifier is optional although the unit is mandatory. — where no unit is cited, and for event catalogue entries, since PREMIS requires no particular event. Where Level is stricter than the PREMIS obligation, the requirement is this profile’s own.
Name, location & description The requirement name in bold, the element or attribute path within premis.xml in code font (for a process rule, the artefact or pipeline step it governs), and the rule as applied in this profile, with values and examples.
Cardinality How many times the element may or must occur within its parent; for a process rule, per PREMIS file or per version as stated.
Level The requirement level (see Conventions).

Cardinality specifies how many times an element may or must appear:

Value Meaning
1..1 Exactly once: mandatory, one occurrence
1..n One or more: mandatory, may repeat
0..1 Zero or one: optional, at most one occurrence
0..n Zero or more: optional, may repeat

DPM1 — — Writing sides — metadata/preservation/{JOB_ID}_premis.xml
The preparation side writes the PREMIS file for each SIP, complete by the end of step 7; the ingest side extends it at step 9 (the SIP→AIP transformation). Nothing outside these two sides writes PREMIS. PREMIS is updated by versioning: each new version carries a new premis.xml at the same logical path, containing its predecessor’s content plus the version’s additions (DPM2, DPM4); a premis.xml already committed to OCFL is never modified. Events of the repository itself on a held AIP, such as a later fixity audit, are outside release 1 (see Open items).		 — MUST
DPM2 — — Creation from the held predecessor — steps 6–7
For v1 the preparation side writes a new file. For v2 and later it reads the head-version premis.xml from the OCFL object and writes the new SIP’s PREMIS as that file plus the elements of the new version (DPM4). It records in every bag, in bag-info.txt, the OCFL version of the object the SIP was built on, as DPR-Predecessor-OCFL-Version: vN, or DPR-Predecessor-OCFL-Version: none for a new object. The ingest side commits the SIP only if the value matches the object’s current state: vN equal to the head in the root inventory.json, or none with no object at the storage path. The preparation side has read access to DPR/AIP; only the ingest side writes to it.		 — MUST
DPM3 — — Ingest appends, never regenerates — step 9
After the bag has been verified (DPM112), its DPR-Predecessor-OCFL-Version confirmed against the object (DPM2), and its identifiers confirmed against the SIP (External-Identifier equal to the SIP’s UUID, as the SIP METS @OBJID and DPM111’s sip_id; Internal-Sender-Identifier equal to the intellectual entity’s JOB_ID; DPR-Object-UUID equal to its UUID; a mismatch holds the bag), the ingest side parses the SIP’s PREMIS and appends the ingest fixity verification (DPM112) and AIP creation (DPM113) events, with a description of each of their executing programs not already described (DPM78). It then validates the result (DPM10), rewrites METS.xml as [METS-PROFILE] sets out (DME9: the new PREMIS digest and size, the AIP package type and identifiers; DPM11), checks digest agreement (DPM12) and commits the version with its commit record (DPM14). A failure at any point holds the bag and commits nothing. Every element received in the SIP’s PREMIS is carried forward unchanged; preparation-side provenance exists nowhere else.		 — MUST
DPM4 — — Append-only across versions — premis/*
A version’s PREMIS contains every element of its predecessor, unchanged in content, plus new elements. Existing object, event, agent and rights elements are never deleted or altered, with one exception: a new relationship may be added to an existing object, after its existing relationships (e.g. includes on a representation that gains a file). An object no longer in the head state remains described: it is still held in an earlier version.		 — MUST
DPM5 — — Correction by addition — premis/*
A mistaken element is never edited or removed. It is corrected by a new OCFL version, with selection basis premis_correction, whose PREMIS adds a PREMIS correction event (DPM114) identifying the mistaken element and stating the correct value; the mistaken element remains in every version that contained it. A correction is authorised by the operator. Where the correct value names an agent or object not yet described, that agent or object is added in the same version. A reader of PREMIS applies every correction event to the element it identifies; a correction may itself be corrected in the same way. Corrections apply to PREMIS only: a wrong content file or DOME record is replaced through its own version type (for a defective master, master_reconversion), not through a correction.		 — MUST
DPM6 — — Scope of PREMIS — premis/*
PREMIS records only the objects, relationships, events, agents and rights statements defined in this profile’s tables. Facts excluded from PREMIS are recorded as set out under Provenance outside PREMIS.		 — MUST
DPM7 2.5.1 Optional Successful outcomes only — event/eventOutcomeInformation/eventOutcome
Every event in PREMIS has the outcome success. An event that succeeded only after warnings or flags were reviewed and accepted (a veraPDF warning at conformance validation, a flagged difference at fidelity review) is success, with an eventOutcomeDetailNote naming each accepted warning or flag, the reviewer and the adjudicated reason. Failed attempts are recorded in the run report (DPM6).		 1..1 per event MUST
DPM8 — — Mint once — every UUID written to PREMIS
Every object, representation, file, event, agent, batch, SIP and rights statement has one uuid4, given once and kept permanently, including through corrections (DPM5). A UUID is never given to a second entity, except the object’s UUID, which names both the intellectual entity and its AIP (DPM23): a changed file is a new file with a new UUID, never the identifier of the file it replaces at the same logical path; a new software version is a new agent with a new UUID. Object, representation, file, event, batch and SIP UUIDs are minted by the preparation and ingest sides when the entity is created. The AIP has no UUID of its own: it is identified by the intellectual entity’s UUID, minted by the preparation side with ingestion start (DPM102) in the object’s first version and carried, in urn:uuid: form, as the OCFL inventory id and the root METS @OBJID (DPM23). An AIP version is identified by that UUID and its OCFL version (e.g. v2), without a UUID of its own. Agent UUIDs are minted in the agent registry when the agent is registered and are only copied into PREMIS (DPM81). Every UUID is checked against the UUID registry and entered in it when minted, before it is used (DPM9); a UUID already present halts the item for review and is never resolved by re-minting.		 — MUST
DPM9 — — UUID registry — [UUID-REGISTRY]
One append-only registry records every UUID minted in the repository, one row per UUID, with the columns set out under The UUID registry. It is kept as a CSV file or as a table in an SQL Server database (see Open items). A row is appended when the UUID is minted, before it is used; it is never edited or removed, including for UUIDs given to attempts that never reached an AIP. Concurrent writers are serialised: by a file lock for a CSV file; by the database’s transactions for SQL Server, where a unique constraint on uuid also enforces uniqueness and writers are granted insert but not update or delete. The preparation and ingest sides append rows for the UUIDs they mint; whoever registers an agent appends a row for its UUID at registration. The UUID registry reserves identifiers only: what a UUID describes is recorded in PREMIS or in the agent registry.		 1..1 per repository MUST
DPM10 — — Schema validity — metadata/preservation/{JOB_ID}_premis.xml against schemas/premis.xsd
The preparation side validates premis.xml against the package-local PREMIS 3.0 schema before bagging; the ingest side validates it again after appending its events, before commit. Validation uses only the schemas in the package’s schemas/ folder (DPM18, DPM19), and also checks that the file contains no semantic unit at level NOT USED (see Conventions). An invalid file halts the item on the preparation side; on the ingest side it commits nothing and holds the bag.
Example: a file object carrying storage is valid against the PREMIS 3.0 schema, but storage is NOT USED in this profile (DPM64), so the file fails this check.		 — MUST
DPM11 — — PREMIS and METS change together — mets/amdSec/digiprovMD/mdRef/@CHECKSUM
Every version writes a new premis.xml (DPM1), whose SHA-512 differs from its predecessor’s; the root METS reference to it (@CHECKSUM, and @SIZE where given) is therefore rewritten in the same act, and the two are committed in the same OCFL version. The rest of the METS rewrite is governed by [METS-PROFILE] (DME9).		 — MUST
DPM12 1.5.2.2 Mandatory Agreement with the OCFL inventory and the predecessor — object/objectCharacteristics/fixity/messageDigest
Before commit, the ingest side checks that PREMIS agrees with the OCFL inventory on the held files, and with the predecessor’s PREMIS:
(a) every file in the new version, except {JOB_ID}_mets.xml, metadata/preservation/{JOB_ID}_premis.xml and the files under schemas/, is described in PREMIS by a file object with the same filepath (DPM41) and the same SHA-512;
(b) every file held in the new version or any earlier one — each logical path with each SHA-512 it has had in any version’s state, except {JOB_ID}_mets.xml, metadata/preservation/{JOB_ID}_premis.xml and the files under schemas/ — is described by a file object with that filepath and SHA-512 (a superseded file; see Superseded files), and every file object with a filepath is one of them;
(c) every master new in the version whose derivation (DPM75) relates it to a published PDF already described in the predecessor belongs to a master_reconversion version, and its normalisation names the master it supersedes (DPM106);
(d) in v2 and later, every object, event and agent element of the head version’s premis.xml is present in the new one, unchanged except for relationships added after an object’s existing ones (DPM4).
If any check fails, nothing is committed and the bag is held. METS.xml, premis.xml and the files under schemas/ are not described in PREMIS; their fixity is recorded in the inventory only.		 1..1 per held file MUST
DPM13 — — Encoding — metadata/preservation/{JOB_ID}_premis.xml
Encoded in UTF-8 [RFC3629] without a byte-order mark, opening with the XML declaration <?xml version="1.0" encoding="UTF-8"?>; text in Unicode Normalization Form C [UAX15]; LF line endings. Values copied from other sources (DOL file names in originalName, values taken from DOME) are normalised to NFC when written.		 — MUST
DPM14 — — Commit record — inventory.json: versions/vN/created, user, message
The commit record is the block the OCFL inventory holds for each version. It is not PREMIS: the commit is recorded in the inventory, not as a PREMIS event (Provenance outside PREMIS). The ingest side writes it at commit:
• created — the commit time, in UTC [RFC3339] with the Z designator (e.g. 2026-10-12T09:14:03Z);
• user/name — the name of the person who authorised the commit: the authorizer of the version’s AIP creation event (DPM113), as registered in the agent registry;
• user/address — a mailto: URI [RFC6068] with that person’s e-mail address, as registered in the agent registry. This follows [OCFL] §3.5.3.1, under which user identifies the person committing the version; the software that commits it is recorded in PREMIS as the executing program of the AIP creation event;
• message — the version’s selection basis, a space, an em dash, a space, and a short description (e.g. new_document — initial ingest (en)).
Because PREMIS records the same facts in its own events, the commit record must agree with the version’s premis.xml:
• Agent — user/name and user/address equal the name and e-mail address in the agent-registry row of the authorizer of the version’s AIP creation event (DPM113), identified by its linkingAgentIdentifierValue;
• Selection basis — the selection basis at the start of message equals the selection_basis value in the eventDetail of the version’s SIP creation event (DPM111);
• Time — the eventDateTime of the version’s AIP creation event is no later than created. The two are not equal: the event is written into premis.xml before the version is committed.
The ingest side checks all three before commit; a failure commits nothing and holds the bag.		 1..1 per version MUST
DPM117 — — PREMIS of the AIP version — metadata/preservation/{JOB_ID}_premis.xml as committed at step 9
The premis.xml committed in an AIP version created from a SIP is the SIP’s premis.xml with exactly these additions, appended by the ingest side: the ingest fixity verification event (DPM112), the AIP creation event (DPM113), and a description of each executing program of those two events not already described (DPM78). Nothing else differs from the SIP’s file. It is the file read as the predecessor by the next version (DPM2).		 1..1 per AIP version created from a SIP MUST

9 Modification by version type

Versions. An OCFL version is “the state of an OCFL Object’s content” [OCFL §2], not an edition of the document, and once created it is not changed: “the contents of a version directory are expected to be immutable” [OCFL §3.3]. This repository processes each language version separately as it is published on DOL, so each creates a new version of the object, the first creating v1. An added language is therefore a new version (language_added), as is a revised one (modified_files); the selection basis, not the version number, says which. This profile calls the creation of a version by the ingest side its commit, and the version’s created, user and message in the inventory its commit record (DPM14); OCFL itself does not use the word.

The selection basis of the version decides what is appended. In every case DPM4 applies: all predecessor elements are carried forward unchanged.

Version type Basis Objects appended Events appended Relationships appended
New object (v1) new_document IE; rep_1, rep_2; every held file; each published PDF DPM102–DPM109, DPM116, DPM111–DPM113 all, per the Relationship catalogue
New language version (v2+) language_added (proposed) the new language’s held files and published PDF; new reports; new DROID report DPM103–DPM109 for the new files; DPM110 if DOME changes; DPM111–DPM113 includes on rep_1/rep_2; derivation and dependency for the new files
Re-issue (v2+) modified_files the changed language versions’ new published PDFs, masters and reports; new DROID report as above, for the changed set only; DPM111 carries changed_languages as above
Metadata change (v2+) metadata_change the new DOME file DPM110; DPM111–DPM113 none
Derestriction (v2+) derestriction the new DOME file; rights statement (pending) DPM110; DPM111–DPM113 rights link (pending)

Withdrawal and removal cancel_retain_catalogue, cancel_full_removal, database_full_removal — — Draft; not specified until the policy is settled

Superseded files. A re-issue, a metadata change or a master reconversion writes new bytes at an existing logical path. The new file is a new object with a new file_id (DPM8). The predecessor’s object stays in PREMIS unchanged, since it is still held in its version. The representation gains an includes relationship to the new file; its relationship to the predecessor is not removed. Which file is current at the head is answered by the OCFL head state, not by PREMIS.

13 Glossary

Note

Not final. This glossary is still being worked on: terms, definitions and their sources are to be reviewed and completed.

Definitions are brief; where a requirement or section governs a term, it is cited and prevails. A reference key in square brackets marks a definition based on that source; definitions without one are this profile’s own.

Term Definition
Agent A person, organisation or software version that performs or authorises an event; each is identified by its UUID in the agent registry (DPM78–DPM86); after [PREMIS].
Agent registry The list of every agent’s UUID, name, type and version, from which PREMIS agent descriptions are copied.
AIP Archival Information Package: the object as held in DPR/AIP, stored as an OCFL object; each OCFL version is an AIP version; after [OAIS].
Authoring source The authoring file (e.g. DOCX) acquired from DOL and held in rep_1 as acquired: digested, verified, renamed and identified like any held file, but not normalised; no master is derived from it.
Bag A SIP packaged under BagIt [BAGIT], with a SHA-512 payload manifest verified at ingest (DPM112).
Characterisation Identifying a file’s format, validating it against the format’s specification, extracting its technical metadata, and assessing it for acceptance [DPC-HB]. In release 1 the pipeline performs format identification (DPM109) and validation (DPM107) only.
Commit The creation of an OCFL version by the ingest side; its commit record is the version block of the inventory (DPM14).
Digest The message digest computed from a file’s bytes by SHA-512 [FIPS180-4]: 512 bits, written as 128 lowercase hexadecimal characters. Any change to the file gives a different digest with very high probability, and it is computationally infeasible to find two files with the same digest.
DOL Documents Online, the WTO system from which official documents and their metadata are acquired.
DOME record The descriptive metadata record of the document, held at metadata/descriptive/{JOB_ID}_dome.xml.
Executing program The software that performed an event’s act: the script, or the tool it calls where that tool does the work.
Filepath A held file’s OCFL logical path, relative to the version’s content/ directory (DPM41); after [OCFL].
Fixity Recording a file’s digest and later recomputing it to confirm the bytes are unchanged [DPC-HB].
Format identification Determining a file’s format by matching it against a format registry; here, DROID against PRONOM, recorded as a PUID (DPM49, DPM109) [PRONOM]. Corresponds to the LoC event type format identification.
Held file A file stored in the AIP and described in PREMIS with a filepath.
Ingest side Steps 8–9 of the workflow: bag verification to OCFL commit.
Intellectual entity The WTO official document as a whole; one per AIP (DPM20–DPM26); after [PREMIS].
JOB_ID The object’s local identifier, YYYY_NNNNNN (DPM24).
Master Short for PDF/A preservation master: the PDF/A-2b file held in rep_2, derived from a published PDF by normalisation.
Normalisation Conversion at ingest to a preservation format, here PDF/A-2b (DPM106); distinct from migration, which is obsolescence-driven and outside release 1. PREMIS writes the LoC term normalization.
OCFL inventory inventory.json: the record of each version’s state, the fixity of every file and each commit (see The OCFL inventory); after [OCFL].
OCFL version A state of the object’s stored content, created by any change; not an edition of the document (see Modification by version type); after [OCFL].
Preparation side Steps 0–7 of the workflow, ending with the bagged SIP.
Published PDF The PDF of a language version of a document as published in DOL, from which its PDF/A preservation master is derived. PREMIS records its identifier, digest, size, format and DOL file name, but its bytes are not stored in the AIP (DPM40).
PUID PRONOM Unique Identifier: the PRONOM registry key for a file format, as reported by DROID (DPM55) [PRONOM].
Release 1 The first release of the pipeline: current documents, PDF 1.7 → PDF/A-2b. Not to be confused with v1, the first OCFL version of an object.
Representation A set of files rendering the intellectual entity: rep_1 (authoring sources, as acquired) or rep_2 (PDF/A preservation masters and attachments); after [PREMIS].
Run report The retained per-batch record of facts excluded from PREMIS (see The run report).
Selection basis The reason a version is created, e.g. new_document, recorded on SIP creation (DPM111) and in the commit message (DPM14); values under Controlled vocabularies.
SIP Submission Information Package: the package the preparation side builds for one version, with its own UUID; after [OAIS].
Superseded file A held file replaced at its path by a later version; still held in its earlier version and still described in PREMIS (see Superseded files).
Technical metadata extraction Extracting a file’s technical properties, such as page count, fonts or colour spaces. Not performed in release 1 (DPM62); the corresponding LoC event type is metadata extraction.
UUID registry The append-only list of every UUID minted in the repository (DPM9).
